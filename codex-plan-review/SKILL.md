# 方案的外部对抗评审（codex）

## Overview

方案作者评审不了自己的方案。你写方案时用的那套假设，你复查时还会再用一遍——凭记忆写下的模块名、你以为存在的参数、你默认成立的前提，自查时同样会被默认成立地跳过。这不是不认真，是同源偏差：同一个模型、同一段上下文，产生盲区和漏掉盲区的机制是同一个。

`codex` 是**不同厂商、不同模型、不认识这段对话**的外部评审。这三点各有用处：不同模型 → 盲区不重合；不认识对话 → 不会被你的推理链带着走，会去实际读代码核对；只读权限 → 能核实"方案里写的那个函数到底存不存在"，而这恰恰是方案最常翻车的地方。

代价是它也**看不到**你知道的东西：用户偏好、已经拍板过的决策、上下文里被否掉的方向。所以它的意见是**待核实的线索，不是待执行的指令**。

这条区别是整个 skill 的重心。

## 何时用

**该用**——方案错了要返工的场合：

- 多步实施计划（3 个以上有依赖关系的任务）
- 研究方案 / 实验设计（尤其涉及口径、基线、判据的）
- 重构、迁移、架构变更方案
- 要写进 `docs/plans/`、`docs/` 的长期文档
- **退出 plan mode 之前**——用户批准之后就开始动手了，此刻是最后一道闸

**不该用**——评审成本超过返工成本的场合：

- 单文件小改、bug 修复、加一个参数
- 纯问答、解释代码、查资料
- 一次性探索脚本（`tmp/` 下那种跑完就扔的）
- 用户已经明说「直接做」「不用评审」「先快速试一下」

判断标准不是方案长短，是**做错的代价**。一份 20 行但会污染回测口径的研究方案，比一份 200 行的文档整理方案更该评审。

不确定时就跑——一轮评审几分钟，一次返工几小时。

## 前置：方案必须先落盘

codex 要读方案文件，所以起草稿必须先写成文件。

- 长期方案 → 它最终该在的地方（如 `market_observer/docs/plans/YYYY-MM-DD-<名字>.md`）
- 只在对话里用的方案 → `tmp/plan-<名字>.md`，评审完再决定要不要留

方案里**具体一点**：写清路径、函数名、命令、数字基线。含糊的方案评审不出东西——codex 没法核实"优化一下性能"，但能核实"改 `market_observer/breadth.py:168`"。你写得越具体，它能抓的 repo-mismatch 越多。

用 superpowers 的 `writing-plans` 起草的方案天然满足这一点。

## 评审循环

最多 3 轮。每轮四步，**第 2 步是重心，不能跳**。

### 第 1 步：跑评审

```bash
.claude/skills/codex-plan-review/scripts/codex_review.sh \
  --plan <方案文件> \
  [--round <N>] [--prior <上轮处置记录>] \
  [--mode repo|text] [--focus "重点看数据口径"] \
  [--retries 2] [--fallback-model <m>]
```

- `--mode repo`（默认）给 codex 只读仓库权限，它会去核对方案与代码。**抓 repo-mismatch 全靠这个**，不要随便降级。
- `--mode text` 只喂方案正文。仅在方案完全不涉及本仓库代码时用（纯策略讨论、纯文档结构）。快，但抓不到"这个函数不存在"。
- 产物落在 `<方案目录>/review/<方案名>/`。每次尝试有独立日志 `round<N>-codex.attempt<K>.log`（重试不覆盖），`round<N>-codex.log` 指向最近一次。
- 脚本内置瞬时故障韧性：命中限流/容量/5xx 特征时自动退避重试（默认 2 次追加尝试，45s/90s 退避），最后一次尝试自动降级（给了 `--fallback-model` 就换模型，否则降一档 effort）。重试耗尽退出码 **4**——这是"该走降级路径"的信号，不是让你原样再跑一遍。

**这一步要放后台跑**，并告诉用户在等。实测耗时：读仓库的真实方案 **10-20 分钟**（`xhigh` 强度，方案越具体它读的代码越多，慢是在干活——实测它会为了确认一个前提去跑只读探针）；`--mode text` 约 1 分钟。若走第三方免费 provider，高峰时段可能被 "at capacity" 限流拖长甚至失败（脚本会自己重试）。按 3 轮上限估最坏情况一小时，所以「该不该跑」的判断要在开跑前做完。

**评审运行期间冻结方案文件。** codex 正在读它，期间改动会让本轮结论对最新正文失真（脚本结束时对比方案哈希，被改过会告警）。等待期间发现的要改的点先记进自查笔记，等本轮结束、处置完再统一改；已经改了就在 disposition 里注明"评审期修改"，改动实质影响结论时重跑本轮。

### 评审运行的隔离（脚本默认开启，勿关）

脚本对 codex 施加两层隔离，动因是 2026-08-08 的真实事故：codex 把本仓 AGENTS.md **当成了自己的操作指令**（而非评审材料），照着执行了常驻智能体工作流——加载人格、召回记忆、甚至 `gateway_memory_write` 写入了记忆日记（`-s read-only` 只管文件系统，管不住 MCP 写工具），单轮 token 从常规量级膨胀到 127 万，运行被拉长后又撞上 provider 容量窗口而中断。

1. `-c mcp_servers={}`——评审是无副作用的只读活动，直接清空 MCP 服务器；
2. `-c project_doc_max_bytes=0`——关闭 AGENTS.md/CLAUDE.md 作为**指令**的自动摄入；它们仍以**评审材料**身份出现在提示词的"先读这些"清单里（用于核对方案是否违反仓库约定），reviewer-prompt 里也有对应的身份边界条款。

跑完后脚本会 grep 日志自检：出现任何 `mcp:` 调用都会告警——看到告警要去核查副作用（尤其写操作）并清理。`--no-isolate` 仅供调试，正常评审不要开。

盯进度看 `<out>/round<N>-codex.log`——里面是 codex 正在读哪些文件。这个日志本身有情报价值：**它读的文件如果和方案关系不大，说明方案里的路径写得不够具体，它在自己找**；那往前推一步，你的方案对执行者也同样不够明确。

### 第 2 步：等待期间，自己先过一遍

不要干等。趁 codex 在跑，你自己对方案做一次对抗式复查，**并把结论写下来**。

这么做有两个实在的好处：一是你的自查结论会成为核实 codex 意见的参照——你已经查过的地方，它再提你能立刻判断；二是防止"先看到评审意见再思考"，那样你的判断会被它的措辞锚定。

自查重点和 codex 一样：方案引用的路径/符号/命令是否真的存在（抽查 `文件:行号`）、**数字基线是否重新实测过**——资源数量、目录清单、文件个数这类数字靠记忆写最容易被抓，用 `rglob`/`ls` 重数一遍（实测案例：方案写"27 个因子"，discovery 跳过下划线文件后实际可发现 25 个）、关键前提是否验证过、验收判据能不能证伪、有没有遗漏会让方案失效的情形。

### 第 3 步：逐条核实（重心）

评审结果回来后，对每一条 finding 给出**核实结论**，再决定处置。

**未经核实，一条都不许采纳。** 这不是形式主义。外部评审的两种典型错误各有各的危害：

- **它错而你照做** → 方案被带偏、无谓膨胀，最坏情况是引入它凭空想象的约束
- **它对而你驳回** → 白跑一轮，返工照旧

两种都只能靠去仓库看一眼来分辨。`grep` 一次、读一段代码，几秒钟的事。

核实结论只有三种：

| 结论 | 含义 | 处置 |
|---|---|---|
| **成立** | 拿到了确认证据（能贴出 `路径:行号` 或命令输出） | 采纳，修订方案 |
| **不成立** | 拿到了反证；或它的前提在本仓库/本项目决策下不适用 | 驳回，**写清理由** |
| **无法核实** | 需要跑长任务、需要外部数据、或取决于用户意图 | 挂起，在方案里标注为待确认；涉及用户意图的直接问用户 |

三条具体的判断经验：

- **codex 说"缺了 X"时，先想它是不是不知道我们已经决定不做 X。** 它读不到对话历史。这类意见的驳回率最高。
- **它自述的 `unverifiable` 条目值得你自己去查。** 那些是它想查而查不到的，往往指向真问题——只是它没有证据所以（正确地）没报成 finding。
- **P2 建议默认不采纳。** 除非顺手且确实改进。评审的价值在 P0/P1，被 P2 拖着改方案是常见的注意力浪费。

对待外部意见的态度细节，`superpowers:receiving-code-review` 讲得更全（不要附和式认同、有理由就推回去）。这里的差别只是评审对象是方案而不是代码。

把核实与处置写成 `<方案目录>/review/<方案名>/round<N>-disposition.md`。格式见 `references/artifacts.md`。这个文件有两个用途：喂给下一轮 codex（让它知道哪些已解决、哪些被驳回及为什么），以及作为最终留痕。

### 第 4 步：修订方案，判断是否继续

按采纳的意见改方案正文。**改完先别急着跑下一轮——对本次修订做一次对抗自查。** 实测（2026-08-15，3 轮 15 条）每一轮都有"修订自身引入的新问题"被下一轮 codex 抓出来：命令块路径风格与 `MSYS_NO_PATHCONV` 冲突、哈希排除清单与 robocopy `/XD` 不一致、判据引用了不存在的检查项键名、断言只覆盖了两个同步目标之一。这类问题自己查是几秒钟，被 codex 查就是一整轮评审。至少核对三件事：

- 新写的判据引用的**键名/字段/检查项在代码里真实存在**（grep 一下，别凭记忆写）；
- 新写的**命令块在目标 shell 里语法成立、路径风格前后一致**（例如 Git Bash 下 robocopy 与 `MSYS_NO_PATHCONV=1` 的组合、`/c/` 风格路径与 Windows 原生 exe 的冲突）；
- **前后呼应的清单改了一处后另一处也改了**（排除项、同步范围、白名单、验收条数这类成对出现的清单）。

自查通过后再判断收敛：

> **本轮所有 finding 要么与前轮实质重复、要么核实为不成立 → 停止。**
>
> 只要还有**新增且核实成立**的问题，就再跑一轮（上限 3）。

收敛有可观测信号：新增 finding 数逐轮下降、重申项都是前轮修订的收尾缺口（键名、覆盖面这类）而非新方向、没有新增 P0——满足这些时，处置完最后一轮即可结束评审循环，不必用满 3 轮。

跑第 2/3 轮时必须带 `--round N --prior <上轮 disposition>`，否则 codex 看不到修订上下文，会把上一轮的意见原样再提一遍——那一轮就白花了。

第 1 轮就返回空 findings 是正常且好的结果，直接收尾。

**跑满 3 轮仍未收敛**，说明存在需要人来拍板的根本分歧（通常是方案目标本身有歧义，或 codex 和你对某个前提各执一词）。停下来，把分歧点摆给用户，不要继续刷评审。脚本在 `--round 4` 会直接拒绝执行。

## 留痕与交付

评审产物留在 `<方案目录>/review/<方案名>/`：`round<N>-prompt.md`、`round<N>-review.json`、`round<N>-disposition.md`。

方案正文里**只加一行指针**，保持正文干净：

```markdown
> 本方案经 codex 外部评审 N 轮（YYYY-MM-DD），评审记录见 `review/<方案名>/`。
```

如果某轮评审改变了方案的**形态**（不只是补漏，而是换了做法、砍了范围、加了前置依赖），在指针下面再补 2-3 行说明改了什么、为什么——半年后回看方案时，"为什么不是当初那个更简单的做法"是最值钱的信息。

向用户汇报时说清三件事：跑了几轮、采纳了什么、**驳回了什么及理由**。驳回项尤其要说——那是用户唯一能发现"你替我做了个我不同意的判断"的机会。

## 降级

降级是一条阶梯，前两级脚本自动走，后三级由你执行：

1. **瞬时故障（限流/容量/5xx）**：脚本自动退避重试 + 末次尝试降级（`--fallback-model` 或降一档 effort）。你不需要做任何事。
2. **认证错误（退出码 1，日志含 "Missing environment variable"）**：第三方 provider 的 `env_key` 模式要求环境变量，与 `codex login` 登录态是**两条认证路径**——已登录也可能缺变量。脚本启动时会自动从 `~/.codex/auth.json` 把缺失的 env_key 注入本进程（不打印值、不落盘）；注入后仍失败说明 auth.json 里也没有，先 `codex login` 或手动 export。这不是降级场景，修好认证后原样重跑即可。
3. **重试耗尽（退出码 4）或 codex 不可用**（未登录 / 服务不可达）：不要静默跳过，也不要无脑原样重跑——免费 provider 的容量低谷通常持续几十分钟。告诉用户外部评审暂时跑不了，然后**默认改用内部独立复评**：
   - 派一个**无上下文**的 subagent（general-purpose），提示词就用脚本已生成的 `round<N>-prompt.md`（它是自包含的：评审规则 + 方案路径 + 上轮处置），要求同样"每条 finding 带 `路径:行号` 证据、无证据放 unverifiable"；
   - disposition 文件头部必须注明"**降级：内部复评（同厂商模型，独立性弱于外部 codex）**"，方案正文的评审指针行同样注明；
   - 内部复评的独立性来自"无对话上下文 + 强制读代码"，但同源偏差只消除了一半——如果这一轮做出了形态级修改，等 provider 恢复后补一轮真 codex 复核是值得的。
4. **结果不是合法 JSON（退出码 3）**：脚本会报错并保留原始输出，直接读 `round<N>-review.json` 原文，人工提取意见即可。
5. **方案太大导致超时（退出码 5）**：`--timeout` 调大，或按 Phase 拆开分别评审。降 `--effort` 到 `medium` 是最后手段——评审质量下降得比省下的时间多。

一次实测校准（2026-08-08）：内部复评兜底确认了外部第 1 轮 21 条处置全部落地，并独立抓出 3 条修订自身引入的矛盾——与事后抢救回的 codex 中断结论交叉比对，两者重合 3/6。内部复评是可用的兜底，但它漏掉的另外几条恰好是更依赖"外部视角"的条目，这就是第 3 级里"补一轮真 codex"的依据。

第二次实测校准（2026-08-15，Windows Git Bash，3 轮评审一份 600 行迁移方案）：第 1/2/3 轮分别耗时 1163s / 约 900s / 506s——带 `--prior` 的复评轮明显更快，finding 数 6 → 6 → 3 逐轮收敛，第 3 轮只剩前轮修订的收尾缺口。15 条 finding 全部核实成立、零驳回，同时印证：**方案写得越具体（路径:行号、可执行命令块、实测数字基线），外部评审的命中率越高**——它会真的去 `rglob` 数文件、去只读核对数据中心目录。
