# 评审产物格式

## 目录布局

```
<方案所在目录>/
├── <方案名>.md                    # 方案正文（含一行评审指针）
└── review/
    └── <方案名>/                  # 与方案同名（去后缀），一个方案一个子目录
        ├── round1-prompt.md       # 脚本自动生成
        ├── round1-review.json     # 脚本自动生成
        ├── round1-codex.log       # 脚本自动生成
        ├── round1-disposition.md  # 你手写 ← 唯一需要你写的
        ├── round2-*.…
        └── ...
```

`round<N>-disposition.md` 是你写的，其余由 `scripts/codex_review.sh` 落盘。

## disposition 文件格式

它同时承担两个职责，所以格式要兼顾两边：

1. **喂给下一轮 codex** —— 它需要知道每条意见的下场和原因，才能判断是否已解决、是否该撤回
2. **最终留痕** —— 半年后回看时，"当初为什么驳回了这条"是最值钱的部分

```markdown
# 第 N 轮评审处置

**方案：** `<方案文件相对路径>`
**评审结果：** `round<N>-review.json`（P0×a P1×b P2×c，新增 d 条）
**处置日期：** YYYY-MM-DD

## 逐条处置

### R<N>-F1 — <意见标题>

- **严重度/类型：** P0 / repo-mismatch
- **意见：** <一句话概括 codex 的观点>
- **核实：** 成立 / 不成立 / 无法核实
  <证据。成立要贴 `路径:行号` 或命令输出；不成立要贴反证或说明为何本项目不适用；
   无法核实要说清卡在哪、需要什么才能确认。这一段是整份文件的重心，不要写"确认无误"了事。>
- **处置：** 采纳，方案 §X 改为…… / 驳回，理由…… / 挂起，已在方案标注为待确认

### R<N>-F2 — ……

## 未采纳汇总

| id | 严重度 | 意见 | 不采纳原因 |
|---|---|---|---|
| R<N>-F3 | P1 | …… | 核实不成立：`xxx.py:42` 显示…… |
| R<N>-F5 | P2 | …… | 与本方案目标无关（YAGNI） |

## codex 自述未核实事项的跟进

| codex 的疑虑 | 我的核查结论 |
|---|---|
| …… | 已查 `xxx.py:88`，不成问题 / 确实是问题，已作为新增项写入方案 |

## 方案修订摘要

<这一轮改了什么。列表即可，2-5 条。>
```

## 写 disposition 的三个要点

**核实那一段要能被复查。** 「已确认」「检查无误」等于没写——下一轮的 codex 和半年后的你都无法据此判断。贴出你实际看到的东西：`market_observer/breadth.py:168` 那一行长什么样、命令输出了什么。

**驳回要给理由，而且理由要经得起反驳。** 「不适用」不是理由。「AGENTS.md:63 明令禁止修改 config.py，方案已改走 StrategyBuilder」才是。codex 下一轮会拿着你的理由复核，理由站不住它会重申——那反而是好事，说明这个机制在工作。

**别漏了 `unverifiable` 的跟进。** codex 自述没核实的事项不会出现在 findings 里，容易被整段跳过。但那些正是"它怀疑但拿不到证据"的地方，而你有仓库和上下文，往往一查一个准。实践中这一节挖出的真问题，比 P2 那一堆多。

## 方案正文里的指针

评审记录不进方案正文，正文只留一行：

```markdown
> 本方案经 codex 外部评审 2 轮（2026-08-01），评审记录见 `review/2026-08-01-fee-sensitivity/`。
```

若某轮评审**改变了方案形态**（换做法 / 砍范围 / 加前置依赖），在指针下补 2-3 行：

```markdown
> 第 1 轮评审后的形态变更：原计划直接改 `config.py` 跑批，因违反 AGENTS.md 硬性规则改为
> 经 `StrategyBuilder` 传参；原判据"年化收益下降即敏感"不可证伪，改为与等权基线的衰减斜率对比。
```
