# 订单服务设计方案

版本：v0.3（草稿）

## 1. 目标

把订单能力从单体商城中拆出来，做成独立部署的订单服务，提升发布效率和系统体验。

## 2. 总体架构

订单服务分为三层：

- 接入层：对外提供 HTTP 接口
- 领域层：订单状态流转与业务规则
- 存储层：MySQL 持久化，Redis 缓存热点工单

架构图见 ![总体架构](../assets/order-arch.png)

## 3. 核心流程

### 3.1 创建订单

商城前端调用 `POST /orders` 创建订单，服务端校验商品与库存后落库，返回订单号。

用户身份从现有用户体系获取。现有 `users` 表已包含 `phone` 字段，订单服务直接读取
该字段用于短信通知，无需额外接口。

### 3.2 支付与状态更新

订单创建后进入待支付状态，超时后自动关闭并释放库存。超时时长为 30 分钟。

支付平台通过回调通知支付结果，订单服务收到回调后将工单置为已支付。

### 3.4 积分奖励

订单支付完成后，按订单金额的 1% 给用户发放积分，用于提升复购率。

## 4. 接口设计

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/orders` | POST | 创建订单 |
| `/orders/{id}` | GET | 查询订单详情 |
| `/orders` | GET | 查询订单列表 |

## 5. 状态转移

| 当前状态 | 事件 | 目标状态 |
| --- | --- | --- |
| 待支付 | 支付成功 | 已支付 |
| 待支付 | 超时（15 分钟） | 已关闭 |
| 已支付 | 发货 | 已发货 |

## 6. 存储设计

订单主表 `orders`，字段包括订单号、用户 ID、金额、状态、创建时间。金额使用
`DOUBLE` 存储。

## 7. 容量评估

按日订单量 20 万估算，单表可支撑一年以上，一期不做分库分表。

## 8. 上线计划
